# رؤية المنتج وخطة التطوير

آخر تحديث: 12 يونيو 2026

الاسم المعتمد للمشروع المستقبلي: **نسخة أون لاين**.

هذه الوثيقة هي المرجع المعتمد للأفكار والقرارات المستقبلية الخاصة بتحويل نظام
التصاريح والزيارات من نسخة محلية إلى منتج إنتاجي متعدد الجهات.

التصور البصري المعتمد:
[شاشات نسخة أون لاين](./images/online-version-system-screens-concept.png)

## 1. المرحلة الحالية

- تشغيل النسخة الحالية داخل شبكة داخلية كتجربة فعلية.
- تجربة النظام لمدة من أسبوعين إلى شهر وتسجيل الملاحظات والأخطاء.
- الاحتفاظ بنسخة احتياطية يومية من قاعدة البيانات.
- عدم استخدام بيانات حساسة أو كلمات مرور إنتاجية أثناء الاختبار.
- عدم الانتقال إلى الاستضافة السحابية قبل استقرار إجراءات العمل الأساسية.

## 2. نسخة أون لاين

- تحويل النظام إلى خدمة متعددة الجهات والمواقع.
- لكل جهة نطاق أو عنوان دخول مستقل وهوية بصرية وإعدادات خاصة.
- إنشاء لوحة تحكم مركزية لإدارة الجهات والاشتراكات والتراخيص وحالة الخدمة.
- عزل بيانات كل جهة عن الجهات الأخرى.
- دعم عدة فروع ومواقع وبوابات وإدارات داخل الجهة الواحدة.
- تطبيق الصلاحيات على مستوى الجهة والموقع والإدارة.
- الاحتفاظ بسجل تدقيق للعمليات الحساسة وتغييرات الصلاحيات والإعدادات.

## 3. الهوية والتخصيص

- اختيار نوع الجهة عند إعداد النظام: شركة، جهة حكومية، منشأة إصلاحية، مستشفى،
  أو نوع مخصص.
- رفع شعار الجهة وتحديد اسمها وألوانها بعد التثبيت.
- عدم تضمين أسماء جهات مثل الشرطة أو الأمن العام أو شعارات ثابتة داخل الكود.
- عرض اسم الجهة وشعارها في تسجيل الدخول والتقارير والبطاقات حسب إعداداتها.
- توفير قيم افتراضية عامة لا تفترض طبيعة الجهة المستخدمة.

### ملاحظة تصميم الوضع الليلي

- الوضع الليلي الحالي يستخدم درجات زرقاء كثيرة في خلفية الصفحة والبطاقات
  والشريط الجانبي، مما يجعل الواجهة مشبعة بالأزرق ويضعف وضوح طبقات المحتوى.
- يعتمد مستقبلاً وضع ليلي محايد قريب من أسلوب Codex:
  - خلفية الصفحة: أسود أو رمادي فحمي شديد الداكن.
  - البطاقات والقوائم: درجات رمادية داكنة متقاربة وواضحة الحدود.
  - النص الأساسي: أبيض مريح، وليس أبيض ساطعاً بالكامل.
  - النص الثانوي: رمادي فاتح واضح.
  - الحدود والفواصل: رمادي هادئ.
  - الأزرق أو لون هوية الجهة: يستخدم فقط للروابط والحالة النشطة وزر الإجراء
    الرئيسي، ولا يستخدم كلون عام للخلفيات.
- الأزرار الأساسية يمكن أن تكون بيضاء بنص أسود في الوضع الليلي، والأزرار
  الثانوية سوداء أو رمادية بحد أبيض هادئ.
- يجب الحفاظ على تباين مناسب وسهولة القراءة وعدم تحويل الواجهة إلى أسود وأبيض
  كامل؛ تبقى ألوان النجاح والتحذير والخطر لحالات النظام فقط.
- يطبق التغيير مركزياً من متغيرات الثيم، ثم تراجع جميع الصفحات والبطاقات
  والجداول والنوافذ على سطح المكتب والجوال.

## 4. صفات الزيارة

المقصود بالصفة هو صفة الشخص المراد زيارته، وليس حالة الزائر. يعتمد في الواجهة
عنوان واضح مثل: **صفة الشخص المراد زيارته**.

- في باقة الزوار البسيطة لا يظهر حقل الصفة افتراضياً إذا لم تكن له حاجة فعلية.
- تكون الصفات قابلة للإضافة والتعديل والترتيب والتعطيل لكل جهة.
- لا تظهر صفة `نزيل / سجين` إلا للجهات أو المنشآت التي تحتاجها.
- لا تؤثر صفات جهة على جهة أخرى.
- يمكن توفير قوالب أولية حسب نوع الجهة:
  - الشركات: موظف، مدير، متعاقد، جهة أخرى.
  - الجهات الحكومية: موظف، مسؤول، مراجع، جهة أخرى.
  - المنشآت الإصلاحية: نزيل، موقوف، موظف، جهة أخرى.
  - المستشفيات: مريض، طبيب، موظف، جهة أخرى.
- تحفظ السجلات السابقة حتى عند تعطيل صفة، ولا تحذف الصفة المستخدمة تاريخياً.
- يمكن اختيار `أخرى` مع إدخال وصف عند سماح سياسة الجهة بذلك.

### نموذج حجز الزيارة البسيط

الهدف أن يستطيع الزائر حجز موعد بأقل عدد ممكن من الخطوات، دون طلب بيانات
حساسة لا تحتاجها الخدمة.

الحقول الأساسية:

- اسم الزائر.
- تاريخ الزيارة.
- وقت الزيارة أو الفترة المتاحة.
- الشخص أو القسم المطلوب زيارته.
- سبب مختصر للزيارة، ويجوز جعله اختيارياً.

الحقول الاختيارية حسب سياسة الجهة:

- رقم جوال أو بريد لإرسال تأكيد الموعد وQR.
- اسم الشركة التي يمثلها الزائر.
- عدد المرافقين وأسماؤهم عند الحاجة.
- رقم المركبة إذا كان الحجز يشمل دخول المركبات.

لا يطلب افتراضياً:

- رقم الهوية أو الإقامة أو السجل المدني.
- صورة الهوية أو الجواز.
- تاريخ الميلاد أو الجنسية.
- العنوان الشخصي.
- أي معلومات صحية أو أمنية.

- إذا احتاج عميل متخصص إلى التحقق من الهوية، تكون ميزة منفصلة ومقفلة ولا
  تفعل إلا بسبب واضح وسياسة خصوصية ومدة احتفاظ محددة.
- يولد النظام رقم حجز داخلياً وQR عشوائياً لا يحتوي بيانات الزائر داخله.
- تظهر للزائر رسالة واضحة بالبيانات التي ستُحفظ وسبب استخدامها قبل الإرسال.
- تحدد مدة حذف أو إخفاء بيانات الزيارة بعد انتهائها وفق سياسة الجهة.

### تبسيط الخيارات والمصطلحات

- تزال من نموذج الحجز العام خيارات `موقوف` و`نزيل / سجين` وأي تعريفات أمنية.
- لا تعرض الخيارات الخاصة بجهة معينة لعملاء آخرين.
- تستبدل القوائم الطويلة بخيارات قليلة مرتبطة بنوع الخدمة المفعلة.
- لا يظهر أي حقل شرطي قبل اختيار ما يجعله مطلوباً.
- تستخدم مسميات مفهومة: `موعد الزيارة`، `الشخص أو القسم المطلوب`، `سبب الزيارة`.
- تزال الشروحات التقنية والأكواد الداخلية من واجهة الزائر.
- تكون رحلة الحجز: اختيار الموعد، إدخال الاسم والوجهة، مراجعة، تأكيد.

## 5. عزل البيانات والخصوصية

- بيانات الزوار والتصاريح والملاحظات تخص الجهة المالكة فقط.
- لا تستطيع جهة الاطلاع على زوار أو سجلات أو إعدادات جهة أخرى.
- القرار المعتمد لأول خمس جهات: **نسخة تطبيق وقاعدة PostgreSQL مستقلة لكل جهة**.
- لا تشترك الجهات في جداول المستخدمين أو التصاريح أو الزيارات أو التدقيق.
- لوحة المنصة المركزية تحتفظ ببيانات الاشتراك والتشغيل فقط، ولا تقرأ سجلات
  التصاريح والزيارات الخاصة بالعملاء.
- أي قائمة مركزية مشتركة أو حظر عام تحتاج قراراً نظامياً وصلاحية مركزية خاصة،
  ولا تطبق تلقائياً.
- تشفير الاتصال والنسخ الاحتياطية والبيانات الحساسة، مع تحديد مدة الاحتفاظ.

### سبب اعتماد قاعدة مستقلة لكل جهة

- الكود الحالي لا يحتوي `TenantId`، والمفاتيح الفريدة مثل اسم المستخدم ورقم
  التصريح ورقم الزيارة مصممة لجهة واحدة.
- إضافة عزل منطقي داخل قاعدة مشتركة الآن تتطلب تعديل جميع الاستعلامات والخدمات
  والتقارير، وأي استعلام بلا فلتر جهة قد يسبب تسرباً بين العملاء.
- القاعدة المستقلة توفر عزلاً أقوى، واستعادة ونقل وحذف عميل واحد دون التأثير
  في بقية العملاء.
- يمكن مستقبلاً إعادة تقييم نموذج قاعدة مشتركة بعد نضج طبقة تعدد الجهات
  واختبارات منع التسرب.

## 6. قاعدة البيانات والبنية التقنية

- تستمر `SQLite` في النسخة المحلية التجريبية الحالية.
- تستخدم `PostgreSQL` في نسخة أون لاين.
- يضاف مزود `Npgsql.EntityFrameworkCore.PostgreSQL`؛ المشروع الحالي يدعم
  SQLite وSQL Server فقط، ولا يدعم PostgreSQL حتى الآن.
- تستبدل ترقيات SQLite اليدوية داخل `DatabaseBootstrapService` بترحيلات EF Core
  رسمية قابلة للتطبيق والتراجع والتحقق.
- ينشأ مسار ترحيل موثق من SQLite إلى PostgreSQL مع مقارنة أعداد السجلات
  والمفاتيح والعلاقات قبل اعتماد العميل.
- تحفظ الملفات والمرفقات في تخزين كائنات منفصل بدلاً من قاعدة البيانات.
- تستخدم طوابير للمهام الطويلة مثل التقارير الكبيرة والتنبيهات والمعالجة الخلفية.
- تضاف مراقبة للأخطاء والأداء والسجلات والتنبيهات الصحية.

### شكل تشغيل أول خمس شركات

- `Nginx` يستقبل الدومينات ويحوّل كل شركة إلى منفذ داخلي مستقل.
- لكل شركة خدمة تطبيق مستقلة واسم خدمة مستقل.
- لكل شركة قاعدة PostgreSQL ومستخدم قاعدة بيانات مستقل.
- لكل شركة مجلد ملفات وأسرار ونسخ احتياطية مستقلة.
- أمثلة الدومينات:
  - `alpha.example.com`
  - `beta.example.com`
  - `gamma.example.com`
- تحديث التطبيق يتم بإصدار موحد، لكن ترحيل قاعدة كل شركة ينفذ منفصلاً مع
  نسخة احتياطية واختبار صحة قبل الانتقال للشركة التالية.

### ما لا يوضع في النسخة المركزية

- أرقام الهوية والجوال.
- التصاريح والزيارات والحركات.
- صور التواقيع والمرفقات.
- كلمات المرور أو أسرار قواعد العملاء.
- سجل التدقيق التفصيلي للعميل.

### ما يسمح به في لوحة المنصة

- اسم الجهة ورمزها ونطاقها.
- الخطة وحالة الاشتراك وتاريخ الانتهاء.
- إصدار التطبيق وحالة الخدمة وآخر فحص صحة.
- تاريخ آخر نسخة احتياطية ونتيجة آخر استعادة تجريبية.
- استهلاك تقريبي للمساحة وعدد المستخدمين دون تفاصيلهم الشخصية.

## 7. الاستضافة السحابية

- الخيار المفضل للتجربة التجارية العامة: Microsoft Azure، باستخدام خدمة تطبيق
  مدارة وقاعدة PostgreSQL مدارة وتخزين ملفات ومراقبة.
- عند اشتراط إقامة البيانات داخل السعودية: تقييم Oracle Cloud Infrastructure
  في منطقتي الرياض أو جدة والتأكد من توفر الخدمات المطلوبة داخل المنطقة.
- إعادة تقييم منطقة Azure السعودية عند توفرها الفعلي للعملاء؛ كان موعدها المعلن
  في الربع الرابع من عام 2026 وقت إعداد هذه الوثيقة.
- لا يعتمد مزود نهائي قبل مراجعة إقامة البيانات، اتفاقية مستوى الخدمة، التكلفة،
  النسخ الاحتياطي، وخطة استعادة الكوارث.
- يمكن استخدام Hostinger KVM لتجربة خاصة محدودة، على أن يكون واضحاً أن موقع
  ألمانيا يعني معالجة البيانات خارج المملكة.
- `KVM 2` مناسب لبيئة التطوير أو عميل تجريبي واحد منخفض الاستخدام.
- إذا شغلت خمس شركات صغيرة على Hostinger في خادم واحد، فالبداية العملية هي
  `KVM 4` مع مراقبة الموارد، وليس `KVM 2`.
- وجود جميع الشركات على VPS واحد يعني بقاء نقطة توقف مشتركة؛ العزل في قواعد
  البيانات يمنع اختلاط البيانات لكنه لا يوفر توافراً عالياً عند تعطل الخادم.
- العملاء ذوو المتطلبات العالية يوضعون على خادم مستقل أو بنية توفر عالٍ.
- لا يعتمد خادم خارج المملكة لعميل حكومي أو بيانات حساسة قبل مراجعة نظامية
  لضوابط نقل البيانات الشخصية خارج المملكة وتقييم المخاطر والعقود المطلوبة.

## 8. الأمن والتشغيل الإنتاجي

- إجبار HTTPS ووضع التطبيق خلف بوابة عكسية أو موازن تحميل.
- تخزين الأسرار خارج ملفات المشروع وتدويرها دورياً.
- دعم المصادقة متعددة العوامل للحسابات الإدارية.
- تطبيق أقل قدر من الصلاحيات وفصل مدير المنصة عن مدير الجهة.
- تسجيل الدخول وتغييرات الصلاحيات والاعتمادات والتصدير في سجل تدقيق غير قابل
  للتعديل من المستخدم العادي.
- فحص التبعيات والثغرات قبل كل إصدار وتوقيع ملفات التثبيت رقمياً.
- نسخ احتياطي آلي مع اختبار الاستعادة، وليس الاكتفاء بنجاح النسخ.
- تحديد سياسة تحديث وترحيل قاعدة البيانات تضمن عدم فقدان المحفوظات.
- تثبيت مفاتيح ASP.NET Core Data Protection في مخزن دائم ومشفّر حتى لا تنتهي
  الجلسات أو تتعطل الرموز بعد إعادة تشغيل الحاوية أو نقلها.
- فصل مفتاح QR ومفتاح شاشات العرض وأسرار الاتصال لكل جهة وتدويرها.
- إضافة نقطة فحص صحة للتطبيق وقاعدة البيانات ومساحة التخزين.
- إرسال السجلات إلى مخزن مركزي مع تنبيهات للأخطاء وفشل النسخ الاحتياطي.
- تقييد SSH بالمفاتيح، ومنع دخول root بكلمة مرور، وتفعيل جدار ناري وتحديثات
  أمنية دورية.
- عدم تعريض PostgreSQL للإنترنت؛ يسمح بالاتصال المحلي أو من شبكة خاصة فقط.
- وضع حد لحجم الملفات وأنواعها وفحص المرفقات قبل الحفظ.

## 9. نتيجة مراجعة الكود الحالية

### جاهز ويمكن البناء عليه

- صلاحيات دقيقة وسياسات وصول متعددة.
- تشفير كلمات المرور باستخدام PasswordHasher الحديث مع ترقية الصيغ القديمة.
- حماية CSRF وCookies آمنة ودعم HTTPS وForwarded Headers.
- Rate Limiting على تسجيل الدخول.
- سجل تدقيق يحتوي المنفذ والوقت وIP وحالة العملية وقيم قبل وبعد.
- إعداد هوية الجهة وشعارها وتوقيعها وساعات العمل.
- فصل ملفات التشغيل وقاعدة النسخة المحلية عن مجلد البرنامج.
- اختبارات سلوكية تغطي المسارات الأساسية.

### يحتاج تطوير قبل الإنتاج

- لا يوجد مفهوم شركة أو مستأجر داخل النظام.
- PostgreSQL غير مضاف إلى المشروع.
- لا توجد EF Core Migrations؛ الترقية الحالية مرتبطة بـSQLite وأوامر PRAGMA.
- النسخ والاستعادة داخل التطبيق يعملان لـSQLite فقط.
- الملفات تحفظ محلياً، ولا يوجد تخزين كائنات أو فصل مسارات حسب العميل.
- لا توجد لوحة منصة للاشتراكات أو إدارة الجهات.
- لا يوجد نظام خطط أو حدود استخدام أو تعليق اشتراك.
- صفات الشخص المراد زيارته ثابتة داخل الكود، وتشمل موقوف ونزيل وسجين لكل الجهات.
- لا توجد MFA للحسابات الإدارية.
- لا توجد Health Checks أو مراقبة مركزية أو تنبيهات تشغيلية.
- إعداد `AllowedHosts` مفتوح افتراضياً ويجب تخصيصه في الإنتاج.
- مفاتيح QR تحفظ كملف محلي واحد وتحتاج فصلاً وحماية لكل جهة.
- لا توجد عملية نشر Linux أو Docker معتمدة ومختبرة حتى الآن.

## 10. تخصيص صفات الزيارة

قبل استقبال شركات عامة، تنقل الخيارات الثابتة من الكود إلى جدول إعدادات مستقل
داخل قاعدة كل جهة.

- الحقول المطلوبة: الرمز، الاسم العربي، الترتيب، الحالة، هل يتطلب اعتماداً
  خاصاً، وهل يتطلب توقيع المدير.
- توفر قوالب حسب نوع الجهة، ويمكن للعميل تعديلها وتعطيلها.
- يحتفظ سجل الزيارة بالرمز والاسم وقت الإنشاء حتى لا تتغير التقارير التاريخية
  إذا أعيدت تسمية الصفة لاحقاً.
- تزال آلية استنتاج `موقوف/سجين/نزيل` من نص الغرض تلقائياً للجهات التي لا
  تستخدم هذا النوع.
- في باقة الزوار العامة تكون قائمة الصفات معطلة افتراضياً، ويمكن الاكتفاء باسم
  الشخص أو القسم المطلوب زيارته.

## 11. الخطط التجارية المقترحة

الأرقام النهائية والأسعار قرار تجاري، لكن النظام يحتاج هذه الحدود تقنياً:

| الخطة | الاستخدام المقترح | المستخدمون | المواقع | التخزين | المزايا |
|---|---|---:|---:|---:|---|
| أساسية | شركة صغيرة | حتى 15 | 1 | 5 GB | التصاريح، الزيارات، التقارير الأساسية |
| احترافية | شركة متوسطة | حتى 50 | 3 | 20 GB | المراقبة، الشاشات، تقارير موسعة، نسخ أطول |
| مؤسسية | جهة كبيرة | حسب العقد | متعدد | حسب العقد | SSO، تكاملات، SLA، بيئة أو خادم مخصص |

يلزم لكل اشتراك تخزين: الخطة، تاريخ البداية والنهاية، فترة السماح، حالة
الاشتراك، حد المستخدمين والمواقع والتخزين، والميزات المفعلة.

- عند انتهاء الاشتراك لا تحذف البيانات.
- تتحول الجهة إلى وضع قراءة فقط خلال فترة السماح.
- التعليق الكامل يحتاج رسالة واضحة ومسار تصدير وتسوية.
- لا تعتمد الحدود في الواجهة فقط؛ تطبق داخل الخدمات أيضاً.

## 12. مراجعة السوق الخليجي

توجد في السعودية والإمارات وقطر ودول الخليج حلول متعددة لإدارة الزوار والبوابات.
المزايا المتكررة في عروض السوق هي:

- التسجيل المسبق وإرسال دعوة أو QR للزائر.
- تسجيل الدخول والخروج من كشك ذاتي.
- مسح الهوية أو الجواز والتقاط صورة الزائر.
- طباعة بطاقة زائر مؤقتة.
- إشعار الشخص المضيف عبر البريد أو الرسائل.
- قوائم المنع والمراقبة.
- تتبع حي للزوار داخل الموقع.
- دعم العربية وعدة لغات.
- توقيع الإقرارات واتفاقيات عدم الإفصاح رقمياً.
- إدارة المقاولين والموردين والتوصيلات.
- ربط بوابات الدخول والحواجز والمصاعد وأنظمة التحكم في الوصول.
- تشغيل سحابي أو داخل شبكة العميل.
- تقارير امتثال وسجل تدقيق.

### موقع برنامجنا مقارنة بالسوق

نقاط القوة الحالية:

- يجمع تصاريح الموظفين والمركبات والزيارات في نظام واحد.
- يحتوي سياسة دوام وتأخير وعودة ومخالفات خروج، وهي أعمق من أنظمة استقبال
  الزوار البسيطة.
- صلاحيات وتفويضات وإدارة قيادات وأقسام.
- مراقبة مباشرة وتقارير عربية.
- شاشة بوابة تنفذ الدخول والخروج، وليست لوحة عرض ساكنة فقط.
- اعتماد أجهزة العرض وتعطيلها وتدوير رموزها ومراقبة اتصالها.
- قابل للتشغيل محلياً دون الاعتماد الدائم على الإنترنت.

الفجوات أمام المنافسين:

- لا توجد دعوة زائر ذاتية قبل الوصول.
- لا يوجد كشك استقبال ذاتي.
- لا توجد طباعة بطاقة زائر مدمجة.
- لا يوجد إشعار تلقائي للمضيف عبر SMS أو بريد أو تطبيق.
- لا يوجد مسح هوية/جواز أو تكامل هوية رقمية.
- لا يوجد توقيع إقرار أو اتفاقية زيارة.
- لا توجد وحدة مستقلة للمقاولين والموردين والتوصيلات.
- لا يوجد تكامل جاهز مع الحواجز والأبواب والمصاعد.
- لا توجد خريطة إشغال أو إخلاء طارئ تبين الموجودين داخل الموقع.

### الأولويات التنافسية

1. رابط دعوة وQR قبل الزيارة.
2. إشعار المضيف واعتماد الزيارة من الجوال.
3. كشك ذاتي عربي/إنجليزي مع تسجيل الوصول والخروج.
4. طباعة بطاقة تتضمن الصورة والاسم والجهة ووقت الانتهاء وQR.
5. سجل الموجودين الآن وقائمة الإخلاء والطوارئ.
6. واجهة تكامل للأبواب والحواجز والطابعات.
7. إدارة المقاولين والموردين بعد استقرار مسار الزائر الأساسي.
8. مسح الهوية أو التكاملات الحكومية يضاف فقط عبر قنوات نظامية معتمدة.

## 13. خطة تطوير شاشات العرض

البنية الحالية جيدة من ناحية الثقة بالأجهزة: الشاشة تسجل طلباً، وتنتظر موافقة
الإدارة، ويحفظ رمزها بشكل مجزأ، ويمكن تعطيلها وتدوير الرمز ومراقبة آخر اتصال.
لكن يجب تحويل الشاشة من رابط عام إلى جهاز له وظيفة وسياسة واضحة.

### أنواع الشاشات المطلوبة

- **شاشة البوابة التشغيلية:** للمشغل، وتحتوي البحث والمسح وتنفيذ الدخول والخروج.
- **شاشة الاستقبال:** تعرض الزوار المتوقعين وتتيح تسجيل الوصول والطباعة.
- **كشك الزائر:** واجهة مبسطة دون قائمة النظام، للتسجيل الذاتي ومسح QR.
- **شاشة انتظار عامة:** تعرض رقم الدور أو رسالة الترحيب فقط، دون بيانات شخصية.
- **شاشة مراقبة أمنية:** تعرض الموجودين الآن والتنبيهات والحالات المتأخرة.
- **شاشة إخلاء:** قائمة لحظية بالأشخاص الموجودين داخل الموقع عند الطوارئ.

### إعدادات كل شاشة

- نوع الشاشة والموقع والبوابة والفرع.
- اللغة والثيم وشعار الجهة.
- البيانات المسموح بعرضها.
- الإجراءات التي يسمح للجهاز بتنفيذها.
- وضع ملء الشاشة والتشغيل التلقائي بعد إعادة التشغيل.
- مهلة قفل الشاشة ومستخدم المشغل عند الحاجة.
- آخر اتصال وإصدار التطبيق وعنوان IP.
- مدة العمل دون اتصال وسياسة مزامنة العمليات المؤجلة.

### ضوابط الخصوصية

- لا تعرض شاشة عامة أرقام الهوية أو الجوال أو أسماء كاملة دون حاجة.
- تعرض شاشة الانتظار رقماً أو اسماً مختصراً فقط.
- تخفى البيانات تلقائياً بعد إتمام العملية.
- يربط كل رمز جهاز بجهة وموقع ونوع شاشة محدد.
- لا تسمح شاشة العرض بالانتقال إلى صفحات الإدارة.
- تسجل عمليات المشغل والجهاز معاً في سجل التدقيق.

### تجربة العرض المستهدفة

- اعتماد ثيم ليلي محايد أسود ورمادي وأبيض قريب من Codex.
- تصميم كبير وواضح للمسافة البعيدة واللمس.
- حالات اتصال واضحة: متصل، اتصال ضعيف، غير متصل، مزامنة.
- تنبيه صوتي وبصري اختياري عند السماح أو الرفض.
- عدم تكديس القوائم؛ يظهر الإجراء الحالي والنتيجة وآخر العمليات فقط.
- دعم المقاسات الأفقية والعمودية والكشك والجهاز اللوحي.

## 14. مراحل التنفيذ المعتمدة

### المرحلة 0: تثبيت النسخة المحلية

1. إنهاء الملاحظات الوظيفية الحالية.
2. تجميد مخطط البيانات للإصدار المحلي المستقر.
3. إنشاء اختبارات مرجعية لأعداد ونتائج التصاريح والزيارات والتقارير.

### المرحلة 1: تهيئة Linux وPostgreSQL

1. إضافة PostgreSQL وEF Core Migrations.
2. إنشاء أداة ترحيل SQLite إلى PostgreSQL.
3. إنشاء نشر Linux وخدمة systemd وملف إعداد آمن.
4. إعداد Nginx وHTTPS وHealth Checks وسجلات التشغيل.

### المرحلة 2: منتج جهة واحدة أون لاين

1. نقل الملفات إلى تخزين مستقل.
2. تطوير النسخ الاحتياطي والاستعادة لـPostgreSQL والملفات.
3. جعل صفات الزيارة قابلة للتخصيص.
4. إضافة MFA وإدارة الجلسات والأسرار.
5. تنفيذ اختبار اختراق وضغط واستعادة.

### المرحلة 3: خمس شركات مع عزل كامل

1. أتمتة إنشاء نسخة وقاعدة ونطاق وأسرار لكل شركة.
2. إنشاء سجل مركزي للجهات والخطط وحالة الخدمة.
3. أتمتة التحديث المتدرج والرجوع عند الفشل.
4. منع لوحة المنصة من الوصول إلى بيانات التشغيل التفصيلية.

### المرحلة 4: الخطط والاشتراكات

1. إضافة حدود المستخدمين والمواقع والتخزين والميزات.
2. إضافة دورة حياة الاشتراك والتنبيهات وفترة السماح.
3. إضافة الفواتير أو الربط مع بوابة دفع عند الحاجة.
4. إضافة تصدير بيانات العميل وإغلاق الحساب وفق السياسة.

### المرحلة 5: إطلاق محدود

1. تشغيل عميل تجريبي واحد ببيانات غير حساسة.
2. مراقبة شهر كامل واختبار استعادة فعلي.
3. إضافة عميلين ثم خمسة تدريجياً.
4. عدم التوسع قبل ثبات النسخ والتحديث والمراقبة.

## 15. شروط إعلان النظام إنتاجياً

- نجاح ترحيل بيانات تجريبية كاملة من SQLite إلى PostgreSQL دون فقد.
- نجاح استعادة قاعدة وملفات كل شركة في بيئة منفصلة.
- عدم وجود أي اتصال بقاعدة شركة من خدمة شركة أخرى.
- اختبار صلاحيات يمنع الوصول لكل صفحة وإجراء غير مصرح به.
- اختبار ضغط بالعدد المتوقع مع هامش نمو.
- مراقبة وتنبيه عند توقف التطبيق أو قاعدة البيانات أو فشل النسخ.
- سياسة خصوصية واتفاقية معالجة بيانات وشروط خدمة معتمدة.
- قرار موثق بشأن موقع البيانات ونقلها خارج المملكة.
- خطة تحديث ورجوع مجربة وليست مكتوبة فقط.
- عدم وجود أسرار أو كلمات مرور إنتاجية داخل المستودع أو ملفات النشر.

## 16. قرارات مؤجلة

- مزود السحابة النهائي والمنطقة النهائية.
- آلية التسعير: حسب الجهة أو الموقع أو عدد المستخدمين.
- مدى وجود خدمات مركزية مشتركة بين الجهات.
- التكامل مع الهوية الوطنية أو الدخول الموحد أو الرسائل.
- متطلبات الاعتماد والامتثال النظامي حسب نوع العملاء والبيانات.

## 17. مراجع تنظيمية

- نظام حماية البيانات الشخصية ولوائحه: منصة حوكمة البيانات الوطنية التابعة
  لسدايا.
- لائحة نقل البيانات الشخصية خارج المملكة وتقييم مخاطر النقل.
- يجب مراجعة المتطلبات مع مختص نظامي قبل تشغيل بيانات هوية وزوار حقيقية خارج
  المملكة.
