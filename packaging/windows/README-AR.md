# حزمة ويندوز الإنتاجية

هذه الحزمة مخصصة للنشر الإنتاجي الاحترافي للنظام على ويندوز، مع تشغيل كخدمة ويندوز، وبيانات خارج مجلد البرنامج، وترقية مستقبلية تحافظ على قاعدة البيانات والملفات التشغيلية.

## بنية النشر المعتمدة

- مجلد البرنامج:
  - `C:\Program Files\Vehicle Permit System\`
- مجلد البيانات الدائم:
  - `C:\ProgramData\Vehicle Permit System\`
- قاعدة البيانات:
  - `C:\ProgramData\Vehicle Permit System\data\vehicle-permit-system.db`
- الملفات المرفوعة:
  - `C:\ProgramData\Vehicle Permit System\uploads`
- الإعدادات التشغيلية الخارجية:
  - `C:\ProgramData\Vehicle Permit System\config\appsettings.runtime.json`
- النسخ الاحتياطية:
  - `C:\ProgramData\Vehicle Permit System\backups`

قاعدة البيانات تبقى دائمًا خارج مجلد البرنامج. استبدال ملفات التطبيق أو إزالة البرنامج لا يجب أن يحذف البيانات التشغيلية إلا إذا تم ذلك يدويًا وبشكل صريح.

## نموذج التشغيل

- التطبيق يعمل كخدمة ويندوز باسم:
  - `VehiclePermitSystem`
- الخدمة تُضبط على:
  - `Automatic`
  - `Delayed Auto Start`
  - إعادة تشغيل تلقائي عند الفشل
- أول تشغيل بعد التثبيت أو الترقية ينفذ:
  - تهيئة قاعدة البيانات
  - `schema upgrades`
  - تشغيل الخدمة على الرابط المحلي المعرّف في الإعدادات

## سلوك التثبيت والترقية

### تثبيت جديد

عند التثبيت الجديد:

- ينسخ المثبت ملفات التطبيق إلى `Program Files`
- ينشئ مجلدات البيانات الأساسية داخل `ProgramData`
- ينشئ ملف الإعدادات الخارجية إذا لم يكن موجودًا
- ينفذ تهيئة قاعدة البيانات
- يسجل خدمة ويندوز ويشغلها

### ترقية فوق نسخة موجودة

عند الترقية:

- يكتشف المثبت وجود نسخة سابقة عبر `AppId` الثابت
- يوقف خدمة النظام أو أي عملية باقية للتطبيق
- يأخذ نسخة احتياطية من قاعدة البيانات وملف الإعدادات قبل نسخ الملفات الجديدة
- يثبت الملفات الجديدة فوق النسخة الحالية
- ينفذ `schema upgrades` عبر التشغيل المباشر بـ `--upgrade-db`
- يعيد تشغيل الخدمة

### الحفاظ على البيانات

- الترقية لا تستبدل قاعدة البيانات الموجودة داخل `ProgramData`
- الترقية لا تمس الملفات المرفوعة أو النسخ الاحتياطية أو الإعدادات الخارجية
- إذا وجدت بيانات قديمة تحت المسار القديم `C:\ProgramData\VehiclePermitSystemWeb` فسيتم ترحيلها إلى المسار الجديد تلقائيًا عند الحاجة

## روابط التشغيل الأساسية

- الصفحة المحلية:
  - `http://localhost:5000`
- رابط العملاء الموصى به:
  - `https://vehicle-server`
- تسجيل الدخول:
  - `http://localhost:5000/Account/Login`
- شاشة دخول العرض:
  - `http://localhost:5000/Display/Access`

## إعداد CookieSecurePolicy و HTTPS

القيمة الافتراضية في حزمة التثبيت هي:

```json
"Security": {
  "CookieSecurePolicy": "SameAsRequest"
}
```

استخدم `SameAsRequest` للتشغيل الداخلي، التثبيت الأولي، والدخول المحلي عبر HTTP مثل `http://localhost:5000`. هذه القيمة تجعل كوكي الحماية تتبع نوع الطلب الفعلي، ولذلك لا يتعطل `Login` أو `InitialSetup` عند التشغيل الداخلي.

استخدم `Always` فقط بعد ضبط HTTPS فعليًا، مثل تشغيل النظام خلف reverse proxy يمرر الطلب إلى التطبيق مع `X-Forwarded-Proto=https` من proxy موثوق، أو عند تشغيل التطبيق نفسه عبر HTTPS. عند تشغيل سكربت الخدمة يدويًا مع `Always` يجب تمرير تأكيد صريح:

```powershell
.\tools\install-service.ps1 -CookieSecurePolicy Always -ConfirmHttpsCookieSecurity
```

إذا كانت القيمة `Always` والطلب وصل إلى التطبيق كـ HTTP، فإن نظام antiforgery في ASP.NET Core لا يستطيع إصدار كوكي آمنة فوق طلب غير مشفر، ويظهر الخطأ:

```text
AntiforgeryOptions.Cookie.SecurePolicy = Always, but the current request is not an SSL request.
```

لذلك يقوم المثبت بتصحيح أي إعداد runtime قديم يحتوي على `Always` إلى `SameAsRequest` أثناء التثبيت أو الترقية، ما لم يتم تفعيل HTTPS بشكل صريح ومؤكد. القيمة `None` مدعومة فقط لحالات تشغيل خاصة جدًا، ولا يوصى بها في الإنتاج لأنها تسمح بإرسال الكوكي بدون اشتراط HTTPS.

### روابط شاشات العرض

- يتم ربط أي جهاز عرض من صفحة:
  - `https://vehicle-server/Display/Register`
- بعد اعتماد الجهاز من الإدارة، يستطيع فتح شاشات العرض المعتمدة بدون تمرير مفاتيح في الرابط.
- يفضل استخدام اسم سيرفر ثابت عبر DNS/Hostname بدل عنوان IP داخلي. إذا تغير IP السيرفر، لا تعيد تثبيت العملاء؛ حدّث سجل DNS أو ملف `server-url.txt` في جهاز العميل فقط.

## الحساب الأولي

- مالك النظام (`Super Admin`):
  - لا يوجد اسم مستخدم أو كلمة مرور افتراضية داخل المثبت.
  - في التثبيت الجديد فقط، تظهر شاشة التهيئة الأولى لإنشاء مالك النظام باسم مستخدم وكلمة مرور يكتبها المستخدم.
  - في التحديث، لا يغير المثبت حسابات المستخدمين ولا كلمات المرور ولا صلاحيات `Super Admin`.

ملاحظات مهمة:

- أي تعديل مستقبلي على حسابات النظام أثناء التحديث يجب أن يكون معلنًا في ملاحظات الإصدار، وأن يتم عبر شاشة/إجراء إداري صريح وليس تلقائيًا أثناء التثبيت.
- يجب تدوير مفتاح العرض من صفحة شاشات العرض بعد أول تشغيل إنتاجي عند الحاجة.

## أوامر الإدارة بعد التثبيت

### تثبيت أو تحديث الخدمة يدويًا

```powershell
.\tools\install-service.ps1 -BindAddress 127.0.0.1 -Port 5000
```

### إزالة الخدمة مع الإبقاء على البيانات

```powershell
.\tools\uninstall-service.ps1
```

### فتح النظام محليًا

```powershell
.\tools\open-local.ps1
```

### تشغيل النظام بالخلفية دون فتح المتصفح

```powershell
.\tools\ensure-background.ps1
```

يوجد اختصار باسم `تشغيل النظام بالخلفية` ضمن قائمة ابدأ، ويُنشأ على سطح المكتب أيضًا عند اختيار إنشاء اختصارات سطح المكتب أثناء التثبيت. هذا الاختصار يبدأ خدمة ويندوز إن وجدت، أو مهمة بدء التشغيل الاحتياطية، أو يشغل التطبيق مباشرة في الخلفية كحل أخير.

### تحديث من ملف ZIP

```powershell
.\tools\update-in-place.ps1 -PackageZip "C:\Path\VehiclePermitSystem-1.0.1-win-x64.zip"
```

سيقوم هذا السكربت بإيقاف الخدمة، أخذ نسخة احتياطية من قاعدة البيانات، نسخ الملفات الجديدة، تنفيذ ترقية المخطط، ثم إعادة تشغيل الخدمة.

## خطة الاختبار المعتمدة للنشر

### 1. تثبيت جديد

- ثبّت `Setup.exe` على جهاز نظيف أو بعد إزالة النسخة السابقة
- تحقق من وجود الخدمة `VehiclePermitSystem`
- تحقق من فتح صفحة الدخول محليًا
- تحقق من إنشاء قاعدة البيانات والمسارات الأساسية داخل `ProgramData`

### 2. تحديث فوق نسخة قديمة

- ثبّت إصدارًا أوليًا مثل `1.0.0`
- أدخل بيانات حقيقية للاختبار أو أنشئ سجلًا واضحًا
- ثبّت إصدارًا أعلى مثل `1.0.1` فوقه
- تحقق من:
  - إنشاء نسخة احتياطية في `backups\installer-upgrades`
  - توقف الخدمة أثناء التحديث ثم عودتها للعمل
  - استمرار عمل التطبيق بعد الترقية

### 3. الحفاظ على البيانات

- تحقق أن ملف قاعدة البيانات ما زال في `ProgramData`
- تحقق أن السجلات التي أُدخلت قبل الترقية ما زالت موجودة
- تحقق أن الملفات المرفوعة والإعدادات التشغيلية لم تُفقد

## ملاحظات تشغيلية

- بيئة التطوير تبقى منفصلة عبر `DevelopmentUseLocalData=true` عند استخدام `dotnet run`
- الحزمة الإنتاجية لا تعتمد على قاعدة داخل مجلد التشغيل
- التطبيق منشور `self-contained` ولا يحتاج تثبيت .NET Runtime منفصل على جهاز العميل

## سجلات تشخيص التثبيت

- سجل bootstrap المبكر للمثبت:
  - `C:\ProgramData\Vehicle Permit System\logs\setup-bootstrap.log`
- سجل سكربتات التثبيت والترقية:
  - `C:\ProgramData\Vehicle Permit System\logs\installer.log`
- عند فشل التثبيت قبل إنشاء ملفات داخل `Program Files` غالبًا سيكون سبب التوقف ظاهرًا أولًا في `setup-bootstrap.log`
